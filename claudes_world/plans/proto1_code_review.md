# Code review: Krylov surrogate in Teko (proto1, pre-upstream)

**Written 2026-10-28.** Branch `aidantgould/teko-auto-proto1`: commits `d56e46917d6`,
`12428c7a3d6` and `a4fb6ae9e53`, plus the uncommitted work on top of them (the move into
`src/KrylovSurrogate/`, the `Teko::KrylovSurrogate` namespace, `"Report" > "Print"`, the
Hierarchical Gauss-Seidel form of candidates, and the Teuchos timers: section 9's
"obvious wins").

**How it was reviewed.** Every line of the ten library files, every test file, the
CMake and config changes, all compared with what Teko already does (mostly
`Teko_DiagnosticPreconditionerFactory`, the closest precedent) and with the Teuchos
behaviour the code relies on. clang-format 14 with Teko's `.clang-format` reports
nothing on any of the new or changed files. **Nothing was built or run for this
review**, so every finding below was found by reading. The ones that say "verified"
were checked against Trilinos source.

Line numbers refer to the working tree as of this review. Severity:

- **blocker**: a Trilinos or Teko reviewer would not approve until it changes.
- **major**: a likely review comment that needs a code change or a written answer.
- **minor**: a likely comment, cheap to fix.
- **nit**: style. Fix it if you're already editing the line.

## 1. Summary

The numerical core is sound and well tested: recording at the preconditioner, TSQR with
zero-row padding, the rank-0 SVD, the explicit $K$ with Belos GMRES, and the
round-robin search are all careful about bitwise rank invariance, and the dense
reference tests are strong. A reviewer's comments will mostly be about **how the
feature fits into Trilinos**: how it is gated in the build, what it adds to Teko's
installed API, what happens when a collective operation fails on one rank, and the
parameter list holding an `RCP`.

The findings that matter most, in the order I would fix them:

1. **Hang on a rank-0-only throw** in `reduceOnRankZero` (major, a real bug).
2. **The printed report can describe the wrong preconditioner** when one factory
   builds two preconditioners (major, a real bug).
3. **The feature macro comes from a header, not from TriBITS**, and Teko does not
   declare its TSQR dependency, so in most CI configurations the feature and its tests
   are compiled out (blocker).
4. **Internal functions are installed as public API** (`tpetraBlock`, `scoreCandidates`,
   and the rest) (blocker for most Teko reviewers).
5. **The factory class is named `PreconditionerFactory`**, the same as its base (major).
6. **The factory tests need Amesos2**, an optional Teko dependency, without a guard
   (major).
7. **No user documentation or example** (blocker, already listed as section 9 item 9).
8. **The merged-group form does not say what the surrogate assumed** (major, about
   correctness of meaning rather than of code).

## 2. Cross-cutting

### 2.1 Build integration and the feature guard (blocker)

- [Teko_KrylovSurrogateReport.hpp:36-38](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReport.hpp#L36-L38)
  defines `TEKO_HAVE_KRYLOV_SURROGATE` in a source header from `HAVE_TPETRA_TSQR` and
  `Teko_ENABLE_Belos`. In Trilinos, feature macros come from the package's
  `*_Config.h`, generated by TriBITS. A reviewer will ask for a `#cmakedefine` in
  `cmake/Teko_Config.h.in` next to `Teko_ENABLE_Belos`.
- [cmake/Dependencies.cmake](../../packages/teko/cmake/Dependencies.cmake) does not
  list `TpetraTSQR`. Verified in `packages/tpetra/core/CMakeLists.txt:44-60`:
  `TpetraCore_ENABLE_TSQR` defaults to ON only when the `TpetraTSQR` subpackage is
  enabled. Enabling Teko therefore never turns TSQR on, and the feature is silently
  compiled out unless some other package or the configure line enables it. The
  `trilinos-build` directory was exactly this case (section 8 of the MVP plan).
- **Fix for both at once:** add `TpetraTSQR` to `LIB_OPTIONAL_DEP_PACKAGES`. TriBITS
  then defines `Teko_ENABLE_TpetraTSQR`, the config header can carry
  `#cmakedefine TEKO_HAVE_KRYLOV_SURROGATE` (or test both macros there), and the
  tests' `IF(TpetraCore_ENABLE_TSQR)` becomes `IF(Teko_ENABLE_TpetraTSQR AND
  Teko_ENABLE_Belos)`.
- Ask before opening the PR: which AT2 PR builds have TSQR on? If none, every new test
  is skipped in CI and the reviewers will say so.
- `TpetraCore_config.h` included at
  [Teko_KrylovSurrogateReport.hpp:28](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReport.hpp#L28)
  goes away with the fix above.

### 2.2 Installed API surface (blocker)

`src/CMakeLists.txt` globs `KrylovSurrogate/*.hpp` into `HEADERS`, so all five headers
are installed into the flat Teko include directory. That makes these public, with
Teko's usual compatibility expectations:

- `reduceOnRankZero`, `tpetraBlock`, `buildReducedOperator`, `BlockReduction`,
  `DenseMatrix` and `DenseVector`
  ([Teko_KrylovSurrogateReducedOperator.hpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReducedOperator.hpp));
- `numConfigurations`, `allConfigurations`, `randomConfiguration`, `isValidOrdering`,
  `buildCandidates`, `gaussSeidelSelection`, `scoreCandidates`
  ([Teko_KrylovSurrogateSearch.hpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateSearch.hpp));
- `Handle::attach` and `Handle::getRecorder`, commented "not for users" and "mainly for
  testing"
  ([Teko_KrylovSurrogateReport.hpp:157-165](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReport.hpp#L157-L165)).

Expected comment: "Which of these do you want users to call?" Suggested answer: the
user-facing API is `Handle`, `Report`, `asHierarchicalGaussSeidel` and the factory.
Move the rest into `Teko::KrylovSurrogate::Impl` (or `detail`) and say so in the file
comments. For `attach`, make `PreconditionerFactory` a `friend` and the method
private. `getRecorder` is test-only API: test the first input through a public
quantity instead (for example `rhsCapture`, or a `Report` field holding $\|v_1\|$), or
keep it and document it as a diagnostic.

The headers in `ReducedOperator.hpp` and `Search.hpp` also declare functions that
exist only when `TEKO_HAVE_KRYLOV_SURROGATE` is defined, because the `.cpp` bodies
are wrapped in it. A user who includes the header and calls one gets a link error,
not a compile error. Wrap the declarations in the same guard, or keep them out of the
installed headers (above).

### 2.3 Collective operations and exceptions (major)

Teko reviewers working on MPI code look for one thing first: can one rank throw while
the others wait in a collective?

- **Real bug.** [Teko_KrylovSurrogateReducedOperator.cpp:88-90](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReducedOperator.cpp#L88-L90):
  if `GESVD` fails, rank 0 throws and every other rank waits forever in the
  `broadcast` at line 97. Broadcast `info` with `red.size` and throw on every rank.
- Everything else is rank-consistent, which is worth saying in the PR description,
  because reviewers will check: the `sigma[0] == 0` throw (line 114 of that file) runs
  after the broadcast, the `bHat == 0` throw in `scoreCandidates` sees broadcast data,
  the two `buildReport` checks depend only on collective state, and `Scorer::score`
  catches everything locally, so no candidate's failure escapes a rank.
- Collectivity is documented on `buildReport` and `scoreCandidates`, not on
  `buildPreconditionerOperator`. With `"Print"` on, a rebuild now runs a reduction and
  a search, so the rebuild becomes collective in a stronger way than every other Teko
  factory. Say so in the factory's doc comment.

### 2.4 The handle in the parameter list (major, a design question to answer in writing)

Reviewers will push on this; the answers are worth having ready.

- **Round-trip to XML.** Verified in
  `Teuchos_ParameterEntryXMLConverterDB.cpp:18-55`: writing a list that holds an
  `RCP<Handle>` falls back to the default converter, which prints the pointer, and
  reading that file back throws `CantFindParameterEntryConverterException`.
  An application that echoes its input deck to XML produces a file that cannot be
  reloaded. The same applies to `getValidParameters()` output, which
  has a `"Report Handle"` entry
  ([Teko_KrylovSurrogatePreconditionerFactory.cpp:39](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogatePreconditionerFactory.cpp#L39)).
  Document it, and consider removing the entry before echoing.
- **Lifetime.** The handle holds strong `RCP`s to the recorder (so to the wrapped
  preconditioner and up to `Maximum Samples` full-length vectors) and to the blocked
  operator. Every copy of the parameter list (Stratimikos, Teko, a solver's saved
  list) shares the handle, so the memory lives as long as the longest-lived copy of
  the list, which can be long after the solver is gone. Holding weak `RCP`s
  (`create_weak()`) in the handle, and throwing a clear error in `buildReport` when
  they have expired, is the usual Trilinos answer.
- **Precedent.** Ask the Teko maintainers whether an `RCP` of a user type in a Teko
  parameter list has precedent. MueLu's `"user data"` sublist is the obvious one to
  cite (check its current form before citing it).

### 2.5 Device builds (major, a question to answer)

Trilinos PR testing includes CUDA and HIP builds. Nothing here has run off host.

- Host-only access: `DenseMatrix` throughout, `get1dCopy` in `transposeProduct`,
  `Thyra::DetachedMultiVectorView` in the search. These are small, so host is correct,
  but each `get1dCopy` and each `localMV` is a device-to-host or host-to-device copy.
  Reviewers will ask for the count per `buildReport` (about $N^2 + 3N$).
- Does `Tpetra::TsqrAdaptor` run on device in current Trilinos? Find out before the
  PR. If it falls back to host, say so.
- [tKrylovSurrogateFactory.cpp:106](../../packages/teko/tests/unit_tests/tKrylovSurrogateFactory.cpp#L106)
  asserts that two solves are bitwise identical. That holds on host. KokkosKernels may
  use non-deterministic SpMV or reductions on GPUs, which would make this test flaky
  there. Compare against a tolerance, or guard the bitwise check to host builds.

### 2.6 Documentation (blocker, already planned)

There is no entry in `doc/guide/04-block-preconditioners.md` and no example under
`packages/teko/examples`. Teko's guide was just rewritten upstream (`76bac850f94`,
"further improve documentation"), so its maintainers will expect a new preconditioner
type to appear there. The example should be the Stratimikos route, since that is how
most applications will meet it.

### 2.7 Scope and size of the PR (major, a process comment)

About 1500 library lines and 1100 test lines for a research feature in a production
package. Expect "can this be split?" A natural split: (1) recorder, handle, factory
and report with only $\hat{C}$ and $\hat{b}$; (2) the search. Also expect a request to
mark the type experimental in its documentation, and a question about who maintains
it.

### 3.1 [Teko_KrylovSurrogateReport.hpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReport.hpp)

- **L31, nit.** `Teko_Utilities.hpp` is a heavy include for a report header. It is
  needed only for `BlockedLinearOp`. Forward-declare it, or accept it, since every
  Teko header does the same.
- **L47-65, minor.** `Options` lives in the report header but is the factory's
  parsed parameter list. It sits here only because `Handle::attach` takes it. Fine,
  but a reviewer may ask, and the doc comment should say why.
- **L64, nit.** Two members declared on one line with a single doc comment.
  Doxygen attaches `//!` only to the first. Split them.
- **L89-91, minor.** `status` is a `std::string`, and the comment lists its four
  values. The search already has an enum internally
  ([Search.cpp:36](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateSearch.cpp#L36)).

  compare strings and a fifth status can't be misspelled.
- **L90, minor.** `"max iterations"` is reported for every non-converged Belos

  `"not converged"`, or distinguish the cases.
- **L93, minor.** The comment says $\|\hat{b} - K y\| / \|\hat{b}\|$. The value is

  precisely the distinction wiki `belos-residual-verification` is about.
- **L98, minor.** Each candidate carries a full `ParameterList`. With the default 100
  candidates that is 100 lists, each with $G$ sublists, produced whether or not anyone
  prints them. Cheap enough, but a lazily built accessor

  avoid storing the inverse type names in every candidate.
- **L103, major.** `blockSizes` is `std::vector<int>`, filled from
  `getGlobalNumElements()` with a `static_cast<int>`
  ([ReducedOperator.cpp:160](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReducedOperator.cpp#L160)).
  Blocks over $2^{31}$ global rows exist in the applications this targets, built with
  `GO = long long`. Use `Tpetra::global_size_t` (or `long long`) here and in
  `toParameterList`.
- **L116, nit.** `searchRanks` duplicates `comm->getSize()`. Keep it if the report is
  meant to be logged without context, but say so.
- **L146-173, major.** See 2.2 (`attach`, `getRecorder`) and 2.4 (lifetime).
- **L168, nit.** A private default constructor plus a static `create()` prevents
  stack instances, which is right for an object shared through `RCP`. Say why in a
  comment, or reviewers will ask.
- **L175-176, nit.** `}  // namespace KrylovSurrogate` and then
  `}  // end namespace Teko`. Pick one form. Teko's own files use `// end namespace`.

### 3.2 [Teko_KrylovSurrogateReport.cpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateReport.cpp)

- **L31-54, major (meaning).** `asHierarchicalGaussSeidel` emits a configuration that
  is only what the surrogate scored when every inverse is exact:
  - the surrogate assumes an exact solve of each singleton block
    ($\hat{C}_{jj} = I$), and an exact solve of each merged group's principal block of
    $\hat{\mathcal{C}}$;
  - the test passes `"BGS"` as the merged inverse
    ([tKrylovSurrogateFactory.cpp:265-269](../../packages/teko/tests/unit_tests/tKrylovSurrogateFactory.cpp#L265-L269)),
    which is a Gauss-Seidel sweep inside the group, not the exact merged solve that was
    scored.

  The function comment, the `"Merged Inverse Type"` documentation in the factory
  header, and the test should say that the prediction assumes a direct (or tight
  iterative) solve of the merged group, and that an inexact one is a different
  preconditioner. The test's own comment says the form "must mean what the surrogate
  scored", so it should use an exact merged inverse.
- **L38, nit.** `ordering.empty() ? 0 : ...` silently accepts an invalid ordering. It
  is public API (2.2), so either call `isValidOrdering` and throw, or document the
  precondition.
- **L45, nit.** `blocks << (members++ ? "," : "") << k + 1` hides an increment in an
  expression. Reviewers flag it. Two statements.
- **L48-51, nit.** Placeholders like `"<Inverse Type>"` end up as XML attribute
  values in `print`. Add a test that the printed XML parses back with
  `Teuchos::getParametersFromXmlString`, which checks both the escaping and the
  "ready to paste" claim in the header.
- **L56-84, minor.** `toParameterList` writes `"Candidate 0"` and onward. Zero-padded
  names, or an `Array` per field, would sort correctly in XML viewers past 10
  candidates. Minor.
- **L86-114, minor.** `print`:
  - `std::left` is undone by `os << std::right`, but the stream's original flags and
    precision are not restored. Save and restore with `std::ios state(nullptr);
    state.copyfmt(os);`, or use `Teuchos::OSTab` and a local `std::ostringstream`.
  - `setw(20)` for the ordering column overflows from 10 blocks on, and the columns
    then run together.
  - It prints "best" even when `candidates[0]` did not converge. Say "no candidate
    converged" in that case.
  - `rate` is printed at default precision. `std::setprecision(3)` with scientific
    format would match how the other numbers are read.
- **L137-140, minor.** Function-local `static` timers are common in Trilinos, but
  some reviewers prefer `Teuchos::TimeMonitor::getNewCounter` once per object, because
  static timers outlive `TimeMonitor::summarize` users and complicate `StackedTimer`.
  Teko's Diagnostic factory holds its timers as members. Follow it.
- **L190, minor.** `tpetraBlock(A_, 0, 0)` is null for a zero (0,0) block, which then
  crashes. `buildReducedOperator` already rejects a zero diagonal block first, so this
  is unreachable today. Take the communicator from `A_->range()` (via
  `Thyra::SpmdVectorSpaceBase`) or from block (0,0) only after the check, so the
  ordering of checks doesn't carry correctness.
- **L203-206, nit.** An unreachable `#else` branch returning an empty `Report` will be
  questioned. With the guard handled as in 2.1, this file can be compiled only when the
  feature is on.

### 3.3 [Teko_KrylovSurrogatePreconditionerFactory.hpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogatePreconditionerFactory.hpp)

- **L70, major.** `class PreconditionerFactory : public virtual
  Teko::PreconditionerFactory`. Inside `namespace KrylovSurrogate`, the unqualified
  name `PreconditionerFactory` now means the derived class, and inside the class body
  it means itself, so any later code there that wants the base must qualify it. Error
  messages and stack traces read `Teko::KrylovSurrogate::PreconditionerFactory`, which
  says nothing at a glance. The precedent the plan cites keeps the full name:
  `Teko::NS::LSCPreconditionerFactory`. Rename it
  `Teko::KrylovSurrogate::KrylovSurrogatePreconditionerFactory`, which also matches the
  file name. (`Handle`, `Report`, `Options` and `RecorderOp` are fine as they are.)
- **L37-63, minor.** The XML example has `value="<Some Block Inverse>"`, which is not
  valid XML. Teko's other doc comments do the same, so it is consistent, but someone
  will copy it.
- **L66-68, minor.** Document that a rebuild with `"Print"` on is collective and runs
  the search (2.3), and that the last solve of a run is never printed, because nothing
  rebuilds after it (3.4, L110).
- **L72-76, nit.** The three-argument constructor accepts `Options` without
  validating them (for example `maxSamples < 1`, which `RecorderOp` checks later, or
  `orderings`, checked only at build). Validate in one place.
- **L78-84, nit.** `virtual` without `override` matches Teko. A reviewer who runs
  clang-tidy's `modernize-use-override` may ask for `override` on new code.
- **No `getValidParameters()`.** `Teko::PreconditionerFactory` is a
  `Teuchos::ParameterListAcceptor`, and the list exists as `validParameters()` in an

### 3.4 [Teko_KrylovSurrogatePreconditionerFactory.cpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogatePreconditionerFactory.cpp)

- **L33-61, minor.** The valid list has types and defaults but no ranges. Teuchos
  validators (`Teuchos::EnhancedNumberValidator<int>` for `"Maximum Samples"` and
  `"Candidate Count"`, `<double>` for the two tolerances) would reject a negative
  candidate count or a tolerance $\ge 1$ at parse time, with the standard message.
  Today `"Candidate Count" = -5` is accepted and quietly scores only the three
  mandatory candidates (3.9, L244).
- **L72-80, major.** In the `#ifndef TEKO_HAVE_KRYLOV_SURROGATE` branch the function
  ends with `TEUCHOS_TEST_FOR_EXCEPTION(true, ...)` and no `return`. That macro
  expands to an `if` around the `throw`, which compilers may not treat as always
  taken, so `-Wreturn-type` (control reaching the end of a non-void function) is
  likely. This branch has never been compiled: every build so far had the feature on.
  Some Trilinos PR builds turn warnings into errors, and the feature-off
  configuration is the one CI is most likely to build (2.1). Add
  `return Teuchos::null;` after it, or a plain `throw`, and compile it once with the
  feature off.
- **L77-79, nit.** The message names `Trilinos_ENABLE_TpetraTSQR=ON` but not
  `Teko_ENABLE_Belos=ON`. Give both CMake options.
- **L91-92, minor.** A double loop calling `tpetraBlock` only for its throw reads
  as dead code. A named helper (`checkBlocksAreTpetra(blo)`) or a comment at the loop
  rather than at the call. `buildReducedOperator` fetches the same blocks again, so
  the check could live there instead, at the cost of reporting the error later (at
  `buildReport` rather than at build). Build time is better, so keep it here, named.
- **L93-97 and Search.cpp L225-233, nit.** Orderings are validated twice with two
  different messages. Keep one (the factory's, at build time), and keep the more
  helpful of the two messages.
- **L99, nit.** State key `"krylovSurrogateOp"`. Matches `"diagnosticOp"`. Fine.
- **L105-116, major (real bug).** With `"Print"` on, the rebuild branch prints
  `handle_->buildReport()`, the report of **whatever the handle is attached to**,
  then clears **this** preconditioner's `recorder`. The handle is attached to the
  preconditioner most recently built by this factory. When one factory builds two
  preconditioners (an inverse library entry used for two blocks, or
  `Teko::buildInverse` called twice), rebuilding the first prints the second's
  samples, and the first's are cleared without ever being reported. The same happens
  when a user shares one handle between two sublists. Fix: build the printed report
  from the local `recorder` and `blo` (a free function taking recorder, operator and
  options, which `Handle::buildReport` then calls too), not through the handle. Add a
  test with two preconditioners from one factory.
- **L110, major (usability).** Printing happens only at a rebuild, so a run with one
  solve, or the last solve of any run, prints nothing. The XML-only user this option
  exists for sees no report for the common case of a single solve. There is no clean
  hook: Belos does not tell the preconditioner the solve ended, and printing from a
  destructor (as `DiagnosticLinearOp` does) would run a collective search during
  destruction, possibly after `MPI_Finalize`. At least document it prominently. A
  reviewer may suggest an opt-in `"Print Every N Samples"` or printing when the sample
  cap is first reached.
- **L112, nit.** The rank-0 check is redundant with Teko's default stream, which
  Teuchos sets to root-only output (`Teuchos_VerboseObject.cpp:25`), but correct for
  a user-supplied stream. Keep it, and say why in a comment.
- **L118, minor.** `attach` runs on every build and rebuild, even when the handle is
  the factory's private one and `"Print"` is the only consumer. Fine, but see 2.4 on
  what it keeps alive.
- **L123-125, minor.** `validateParametersAndSetDefaults` on a copy is the standard
  pattern, but the user's list is never given the defaults, so a later
  `getNonconstParameterList()` or a printed "used parameters" list will not show
  them. `setParameterList` in the base class stores `paramList_`. Check what
  Stratimikos shows with `"Print"`-style echoing and decide whether that is wanted.
- **L133-139, minor.** When the user gives no handle, the factory makes one. One
  `initializeFromParameterList` call per factory, so each factory owns one private
  handle. Correct, but this is the case the L105 bug bites hardest.
- **L147, nit.** `"Maximum Samples" < 1` is checked here and again in `RecorderOp`'s
  constructor. One validator (L33) replaces both.
- **L159, nit.** `not` as an alternative token. Teko's Diagnostic factory uses it too,
  so it matches, but MSVC needs `<ciso646>` and some reviewers object. `!` is safe.
- **L165-167, nit.** `"ERROR: \"Inverse Factory\" = ..."` is copied from the
  Diagnostic factory and does not say which factory failed, unlike every other
  message in this file. Prefix it like the others.
- **L170-180, nit.** `getRequestedParameters` and `updateRequestedParameters` forward
  to the wrapped inverse, as Diagnostic does. Correct.

### 3.5 [Teko_KrylovSurrogateRecorderOp.hpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateRecorderOp.hpp)

- **L28-33, minor.** The class comment should state the assumptions the first-input
  capture relies on, since a reviewer from Belos will ask:
  - the solver is right-preconditioned (Belos's default), and its first

- **L50, nit.** `getModifiableOp()` returns the wrapped operator non-const from a
  const method. Matches `DiagnosticLinearOp`.
- **L59, minor.** `getSamples()` returns a non-const view of the internal store, so a
  caller can overwrite the samples. Return `Teuchos::RCP<const
  Thyra::MultiVectorBase<double> >`.
- **L73-75, minor.** `mutable` state written in a `const` `apply` is not
  thread-safe. Thyra operators are not assumed to be, but say so in the class comment.

### 3.6 [Teko_KrylovSurrogateRecorderOp.cpp](../../packages/teko/src/KrylovSurrogate/Teko_KrylovSurrogateRecorderOp.cpp)

- **L31-34, fine.** The const view of `x` follows the lesson in section 8 of the plan.
  Keep the comment.
- **L39, nit.** Exact floating-point comparison of `alpha` and `beta`. Correct here
  (Belos passes literal 1 and 0), but reviewers flag it. Use
  `Teuchos::ScalarTraits<double>::one()` and `zero()` for intent.
- **L46-50, fine.** `beta == 0` assigns rather than scales, so a `NaN` already in `y`
  does not propagate. Correct, and a reviewer who knows Thyra's convention will look
  for exactly this.
- **L59, major (memory).** The first apply allocates all `maxSamples_` columns at
  once: with the default 100, that is 100 full-length vectors on the first apply,
  even if the solve takes 8 iterations (proto1's end-to-end case). On a problem
  with $10^8$ unknowns that is 80 GB across the job, allocated up front. Grow the store

## 4. What a reviewer will probably not complain about

Worth knowing, so these don't get reworked out of caution:

- recording at the preconditioner with no Belos change, and the reasoning in the
  recorder's class comment;
- TSQR with zero-row padding instead of a Gram matrix, and the test showing why;
- the rank-0 SVD and the final broadcasts, with their stated reasons;
- `validateParametersAndSetDefaults` against a documented valid list, with recursive
  validation disabled only for `"Orderings"`;
- Teuchos timers named `Teko Krylov Surrogate: ...`;
- formatting: clang-format 14 reports nothing on any of the new or changed files.
